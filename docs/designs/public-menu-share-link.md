## Problem Statement

Dopa Menu's free loop is complete and untested against reality. Six tagged releases, 124
tests, a 90% coverage gate, and no production deployment, no analytics, and no distribution.
Every monetization decision made in two prior reviews is gated on "a validated demand
signal", and the experiment that was supposed to produce one was never written: the
referenced `docs/experiments/monetization-validation.md` does not exist, and the `/plus`
view counter this repo's TODO asks to bot-guard has no route, no table, and no code in any
commit.

The user's ask this session was orientation: "I want to see the stage that it's at and what
comes next." The answer is that the product has no way to be seen by anyone who is not the
author, so no experiment in the backlog can produce a number.

## Scope, stated plainly

This design builds **distribution and activation measurement**: an anonymous public menu, a
copy path into a real account, a public host, and token-attributed events. It does **not**
produce the money signal that unblocks the monetization deferrals, and it must not be
described as if it does. The money measurement — a pricing page, a deposit path, a refund
policy and a weekly reconciliation owner — is a separate design that runs only after this one
has produced traffic. Premise 1 (money is the unit of evidence) is unchanged; this design is
the precondition for testing it, not the test.

## What Makes This Cool

The menu, not the app, becomes the shareable artifact. `/m/{token}` renders a real person's
four courses as a menu with an author's name on it, readable with no account, and each item
is one tap: "Order · 5 min". Under it, "Copy this menu" puts all of it into the visitor's own
account in one click — no cold start, no empty state, no tutorial.

That single page is simultaneously the traffic source, the acquisition path and the measuring
instrument, and it is the free growth loop the 2026-10-27 review already reserved. A print
stylesheet for that one page is a small extra; it does not by itself deliver the deferred
"printable menu from the app" feature.

## Constraints

- The app records no events at all, so "did anyone use it" is currently unanswerable.
- `anyRequest().authenticated()` means every useful route sits behind Keycloak; a stranger
  cannot reach the product without an account.
- **Self-registration is disabled.** `keycloak/realm-dopamenu.json` sets
  `registrationAllowed: false` and `resetPasswordAllowed: false`. There is no "Create
  account" path today, so "copy this menu into your account" is unreachable for a new
  visitor until the realm changes.
- **The realm never selects the custom login theme.** The JSON has no `loginTheme` key
  (verified across all git history), so `keycloak/themes/dopamenu` is mounted but inert and
  Keycloak serves its default theme. Any claim about the themed Register link is false until
  `loginTheme` is set.
- **No SMTP is configured** anywhere (no `smtpServer` in the realm, nothing in
  `compose.keycloak.yaml`), so Keycloak cannot deliver a password-reset email. `verifyEmail`
  is absent and therefore false, which is what lets registration work without mail.
- The stored mood data is contaminated: `OrderDialog` sets `moodBeforeDefault = 3` and
  prefills the after-rating from the before-rating, and `OrderStats.from` averages
  `moodLift` across all orders. No aggregate mood number may appear on the public page.
- `MenuOrderService.start(ownerSub, itemId, moodBefore)` resolves the item with
  `findByIdAndOwnerSub`, so a visitor cannot start an order on the sharer's item.
- **The dev proxy is not a public front door and must not become one.**
  `deploy/dev-proxy/Caddyfile` serves only `*.dev.dogeared.dev`, answers 403 to any client
  outside RFC 1918 / loopback ranges, and its README explicitly says not to port-forward
  80/443. `deploy/dev-proxy/sites/dopamenu.caddy` matches two dev hostnames only.
- Vanilla Vaadin Flow, server-side Java, no custom JavaScript, one external stylesheet.
- 90% line-coverage gate. `pom.xml` excludes `config/SecurityConfig*`, `AppShell*` and
  `DopaMenuApplication*`; everything else — domain, service, config, UI — is measured.

## Premises

1. **The unit of evidence is money, not interest.** Clicks, waitlist emails and survey
   answers are not demand. The signal that unblocks the monetization deferrals is someone
   paying, however small.
2. **300 views in 30 days is the target threshold, not an observed denominator.** Its source
   is the eng review's own note that the `/plus` bot-guard is "not needed at 300 views / 30
   days". No traffic has happened yet; this design's job is to make traffic possible and
   measurable.
3. **Instrumentation is a prerequisite that does not exist.** Minimum events come before any
   pricing question.
4. **Manual reconciliation with a named owner is the accepted method** under ~50 deposits:
   a ledger with a weekly owner, not a webhook.
5. **The money experiment bypasses the insight-hardening debt.** A pricing page only
   *describes* the paid features, so willingness to pay can be tested without touching the
   mood picker or the timezone column.

## Cross-Model Perspective

An independent cold read (in-host subagent; Codex is not installed) made the case that
became this design:

- Its sharpest claim: as sequenced (fix logout → write the demand doc → build the share
  link), "the demand doc will be written before the thing that could ever produce a view.
  That is a doc describing a measurement of a population of zero." The order became
  3 → 2 → 1 as a result.
- It identified the Keycloak wall as structural: account creation is the highest-friction
  step, and the free app is unreachable without an account.
- It proposed the share page as traffic, funnel and instrument in one artifact, plus
  GoatCounter as a pageview/referrer sidecar.
- Where it overreached: it inferred from one phrase that the user's reward loop is "a green
  pipeline, a bumped VERSION" rather than revenue. Plausible, but stated as fact from thin
  evidence.
- Where this design disagrees: `share_view → order_started` measures distribution and
  activation, not willingness to pay. Premise 1 stands.

## Approaches Considered

### Approach A: Read-only public menu

Token table, anonymous `@Route("m")` view rendering the owner's items through the existing
`CourseSection`/`MenuItemCard`, `SecurityConfig` permit for `/m/**`, print CSS. Produces no
numbers, so it fails premise 3. **Rejected.**

### Approach B: Instrumented share loop

A's page plus a `menu_event` table and an `EventService.record(...)` called from the
share-page render, order start, order completion and menu copy, with a `referrer` column.
One datastore, exact per-token attribution by join. **Chosen.**

### Approach C: GoatCounter sidecar, thin events

A's page plus a self-hosted GoatCounter container for pageviews and referrers; Postgres
records only in-app actions. Gets bot filtering and referrer dashboards for free — the chore
the eng review deferred — but adds a second service and datastore, and the funnel becomes a
timestamp-stitched join across two systems. **Rejected** for now; a `referrer` column in B
covers the same question for less operational surface.

## Recommended Approach

**Approach B — instrumented share loop.** Decisions below are commitments, not options.

### Data model

Three new migrations after the existing `V1__initial_schema.sql`, plus one entity field each
on `MenuItem` and `MenuOrder`.

- `V2__menu_share.sql` —
  `menu_share(id, owner_sub, token, display_name, created_at, revoked_at)`.
  - **One active link, rotatable:** `create unique index on menu_share (owner_sub) where
    revoked_at is null`. A revoked row frees the slot, so rotation is revoke-then-create. The
    constraint enforces the cap; no service logic.
  - **Author name source:** `display_name` is captured at share time, pre-filled from
    `CurrentUser.displayName()` and editable by the owner before saving. The anonymous page
    never calls Keycloak and never exposes more than that field. Publishing the name is an
    explicit opt-in act of sharing.
  - **Token:** 16 bytes from `SecureRandom`, Base64URL without padding (22 chars). At 128
    bits, enumeration is infeasible, so no rate limiter is built for v1; revocation is the
    response to a leaked link. If counting spam appears later, the mitigation is a write-time
    filter, not a redesign.
- `V3__menu_event.sql` —
  `menu_event(id, occurred_at, kind, owner_sub nullable, token nullable, order_id nullable,
  referrer nullable)`. Kinds: `share_view`, `order_started`, `order_completed`,
  `menu_copied`. `order_id` is what makes start and completion joinable per link rather than
  inferred from timestamps.
- `V4__share_attribution.sql` —
  `alter table menu_item add column source_share_token varchar(22)` and
  `alter table menu_order add column share_token varchar(22)`. Both nullable, both plain text
  rather than a foreign key: a revoked share row must not erase the evidence of the traffic it
  produced.
  - **`share_view` is defined as** one row per render of a live token by a request that is
    not the owner's own session and is not a known bot user-agent. It counts refreshes; that
    is a stated limitation, not an accident. The owner's own visits are excluded by session
    check, so "I looked at it" cannot inflate the only number this experiment produces.
  - **Attribution rule, stated because it has a consequence:** a token travels with the
    *item*, not with the visitor. `MenuItem.sourceShareToken` is set when an item is copied
    from a share, and is never overwritten once non-null. `MenuOrderService.start` copies it
    onto the new `MenuOrder.shareToken`, and `complete` copies it onto the event. So a
    returning visitor who orders an item they acquired from link A credits link A even if
    they arrived via link B. With one link live at a time in v1, that ambiguity does not
    arise; it is written down so it is not discovered later as a surprise.

#### Where each event is written, and how the rates are computed

| Event | Call site | Token source |
| --- | --- | --- |
| `share_view` | `ShareMenuView.setParameter` after the token resolves to a live share, skipping the owner's session and known bots | the resolved token |
| `order_started` | `MenuOrderService.start(ownerSub, itemId, moodBefore)`, after `orderRepository.save(...)` | `item.getSourceShareToken()` |
| `order_completed` | `MenuOrderService.complete(ownerSub, orderId, moodAfter, note)`, after the status transition | `order.getShareToken()` |
| `menu_copied` | the copy service method, once per copy action | the intent's token |

`start` keeps its current signature: the token comes from the item it already fetches, so no
new parameter, no dialog plumbing, and attribution survives a visitor who copies an item and
starts the order in a later session.

```sql
-- funnel for one link
select kind, count(*) from menu_event where token = :token group by kind;

-- start rate   = order_started / share_view
-- completion rate = completed orders / started orders
select count(distinct e.order_id)
from menu_event e
join menu_order o on o.id = e.order_id
where e.kind = 'order_completed' and e.token = :token;
```

Both rates are reported with their raw counts, never as a bare percentage, because the
denominators are small enough that a percentage implies precision the data does not have.

### Owner-facing surface

`ManageMenuView` gains a **Share** section: current state (no link / link active), the full
URL with a copy button, `Create link`, `Rotate link` and `Revoke link`. Revoke takes effect
immediately — the visitor sees the dead-token page. Rotate = revoke then create, performed as
one action in the UI. No share management exists in `MainLayout`; `/manage` is where a user
edits their menu, so it is where they share it.

### Public page

- `ShareMenuView`: `@Route("m")` + `HasUrlParameter<String>`, `@AnonymousAllowed`,
  `PublicLayout`, resolving token → live share → owner's non-archived items, rendered through
  the existing `CourseSection`/`MenuItemCard` components.
- `SecurityConfig` permits `/m/**` anonymously — the line that decides whether this can run.
- **Noindex is scoped to this route only.** `PublicLayout` is also `LandingView`'s layout
  (`@Route(value = "", layout = PublicLayout.class)`), so a meta tag there would deindex the
  public front door along with the shared menu. Instead:
  - `@Meta(name = "robots", content = "noindex")` on `ShareMenuView`
    (`com.vaadin.flow.component.page.Meta`, verified present in Flow 25.3.3). The annotation is
    per-route, so `/` stays indexable.
  - `X-Robots-Tag: noindex` set by a small servlet `Filter` mapped to `/m/*`, which also
    covers the dead-token page and any non-HTML response. The filter is a normal class under
    `config/` with a unit test, so the coverage gate is unaffected — `SecurityConfig*` is
    excluded by name, not the whole package.
- One dead-token page for both never-existed and revoked; distinguishing them leaks whether a
  token was ever valid.
- Print styles in `dopamenu.css` cover **this page only** (`@media print` hides nav, footer
  and action buttons). The deferred "print your own menu from the app" feature is unchanged
  and still deferred.

### Anonymous actions and the post-login return path

Both actions require an account, so the interesting design is the handoff.

- **Order:** tapping "Order · N min" stores a single-use intent in the HTTP session —
  `{token, itemId, action: ORDER}` with a 30-minute expiry — then sends the visitor to
  sign-in. After authentication, a `BeforeEnterObserver` on `/menu` consumes and clears the
  intent, re-validates the token against a live share, **copies that one item** into the
  visitor's menu with `sourceShareToken` set, and renders `/menu`.
- **The mood is confirmed, never invented.** The consumed intent does not start an order
  directly. It copies the item, then opens the existing `OrderDialog` at its `BEFORE` phase
  for that item — the same path as clicking an item on `/menu`
  (`Dialogs.open(new OrderDialog(item, orderService, currentUser, this::render))`). The
  visitor sees "How are you feeling right now?" with 3 preselected and must press
  **Start** before `MenuOrderService.start` is called. "Not now" creates no order and no
  `order_started` event.
  - Rejected alternative: passing a sentinel or a silent default into `start`, which is the
    contaminated-mood pattern the Constraints name. `mood_before` is already nullable in the
    schema and `MenuOrder.moodBefore` is already an `Integer`, so a NULL path would also work
    — but then the visitor gets an order with no recorded feeling, and `OrderStats` would have
    to grow null handling for no benefit. Confirmation costs one dialog and keeps the data
    honest.
  - If the account already has an active order, the existing `ActiveOrderException` banner
    appears when the dialog starts and the intent is dropped.
- **Copy:** same intent mechanism with `action: COPY`; on consumption it clones the whole
  menu. No mood is involved.
- **Why copy rather than order the sharer's item:** `MenuOrderService.start` authorizes the
  item by owner. Copy-on-order keeps the per-user ownership model intact rather than adding a
  second authorization path where a token grants write access to someone else's rows.
- **No trusted URL parameters after login.** The intent lives server-side in the session, is
  single-use, expires, and is re-validated against a live share — so there is no
  open-redirect surface and no way to hand a crafted item id to the consumption step.
- `SecurityConfig` changes `defaultSuccessUrl("/menu", true)` to `defaultSuccessUrl("/menu",
  false)` so the saved request is not forcibly discarded; the session intent is what carries
  the action.
- An already-signed-in visitor (including the sharer previewing their own link) skips the
  sign-in hop: the same consumption method runs on the `/menu` navigation, and the sharer
  sees "That's already your menu" instead of a copy button on their own page.

### Copy semantics (v1)

Copies, never live references. Clone `title`, `description`, `course`, `durationMinutes`,
`dopamineLevel`, the dessert timer rule, and `sourceShareToken` from the share being copied,
with `archived = false`. Dedupe on `(title, course)` case-insensitively against the visitor's
existing items, so a second click is a no-op. `sourceShareToken` is stamped **only on the rows
the copy creates**: a reused duplicate keeps whatever token it already had, so a visitor's own
pre-existing dish is never credited to a link that did not supply it (D3 = A). Later edits or
deletion by the sharer do not propagate. Seeded starter items are left
untouched; copied items append to them and remain individually editable or archivable —
replacing the seed set would require tracking which items are pristine, which is more state
than v1 earns.

### Registration

Three realm changes, each written as a change from its current value rather than a claim
about what it already does:

1. `registrationAllowed: false → true`. This is the change that makes any of the above
   reachable by a new visitor. `registrationEmailAsUsername` is absent (false) and stays so.
2. `resetPasswordAllowed` **stays false**. The dev realm has no SMTP server, so enabling the
   "Forgot password" link would hand a locked-out tester a form whose email can never arrive.
   A locked-out tester gets an admin-initiated credential reset through the Keycloak admin
   console (the bootstrap admin credentials are already in `compose.keycloak.yaml`).
3. `loginTheme: "dopamenu"` is added, because the realm currently selects no theme at all and
   the mounted theme in `keycloak/themes/dopamenu` is inert. With `parent=keycloak.v2` the
   Register link is rendered by the upstream template as soon as registration is allowed, so
   no template work is expected — but the page is opened in a browser and checked, and the
   link is added to the theme if the parent does not render it.

Registration returns through the same post-login intent path, so a brand-new visitor goes
from a shared menu to their own populated menu without leaving the flow. `verifyEmail` is
false and stays false: turning it on without SMTP would silently break registration.

## Success Criteria

- From a phone on cellular data with Wi-Fi off, `https://dopamenu.dogeared.dev/` returns 200
  and `https://dopamenu.dogeared.dev/m/{token}` renders a real menu anonymously.
- `curl -sI https://dopamenu.dogeared.dev/m/{token}` returns `X-Robots-Tag: noindex`, and
  `https://dopamenu.dogeared.dev/` does **not** carry it.
- A stranger in a private window can read a shared menu, tap an item, register, confirm a mood
  in the order dialog, and end up with that item copied into their own menu and an order
  running — with the token recorded on `share_view`, `order_started` and `order_completed`.
- "Copy this menu" into a fresh account produces a populated menu in one click; a second
  click changes nothing.
- Rotate and revoke work: an old link stops resolving immediately after revoke.
- `mvn verify` is green with the coverage gate met and no new package excluded.
- After four weeks of one link, shared once into one named community thread, the owner can
  state a view count, a start count and a completed count — or state honestly that the link
  got no traffic. **Outcome "insufficient reach" is a valid, reportable result.**

## Distribution Plan

The build pipeline is unchanged: GitHub Actions, `mvn verify`, coverage gate, auto-tag on
merge. The missing piece is a **public host**, and it is a separate configuration that
replaces the dev proxy for public traffic — the dev proxy stays exactly as it is, LAN-only,
403 to outsiders, and is not modified.

**Hostnames:** `dopamenu.dogeared.dev` (app) and `dopamenu-auth.dogeared.dev` (Keycloak). The
`dogeared.dev` zone is already managed through the Cloudflare token in `deploy/dev-proxy/.env`,
so both are one DNS record each, DNS-only (grey cloud) so Caddy terminates TLS itself.
Registration is the thing that makes a wildcard unnecessary: two explicit names, two explicit
certificates.

**New directory `deploy/public/`,** not a change to `deploy/dev-proxy/`. It is one
self-contained Compose project, `name: dopamenu-public`, and the exact invocation is:

```bash
cd deploy/public && docker compose up -d --build
```

`deploy/public/compose.yaml` is therefore a deploy file rather than an overlay on the root
`compose.yaml`, and it defines all four services:

- `caddy` — `build: .` from `deploy/public/Dockerfile`, a four-line copy of the dev proxy's
  two-stage `xcaddy` build (stock Caddy plus the Cloudflare DNS module), so the public host
  does not depend on the private dev-proxy directory. `ports: ["80:80", "443:443"]` on all
  interfaces — the opposite of the dev proxy's `BIND_IP` binding, and the reason this file
  must not reuse it. `restart: unless-stopped`. Volumes
  `./Caddyfile:/etc/caddy/Caddyfile:ro`, `caddy-data:/data`, `caddy-config:/config`, so
  certificates and the ACME account survive restarts instead of re-issuing into rate limits.
  `CLOUDFLARE_API_TOKEN` comes from `deploy/public/.env`.
- `app` — `build: { context: ../.., dockerfile: Dockerfile }`, publishing **no** ports; Caddy
  reaches it as `dopamenu-app:8080` on the project network, with
  `KEYCLOAK_PUBLIC_URL=https://dopamenu-auth.dogeared.dev`,
  `KEYCLOAK_INTERNAL_URL=http://keycloak:8080` and
  `DB_URL=jdbc:postgresql://db:5432/dopamenu`.
- `keycloak` — publishing **no** ports; Caddy reaches it as `dopamenu-keycloak:8080`.
- `db` — `postgres:17-alpine`, no published ports, its own `dopamenu-public-pg` volume,
  `POSTGRES_USER`/`POSTGRES_PASSWORD: dopamenu`, and
  `./db-init:/docker-entrypoint-initdb.d:ro`.

- `Caddyfile` with one site block per hostname, ACME by DNS-01 reusing
  `CLOUDFLARE_API_TOKEN` (the existing pattern), and **no** `@outside` private-range guard:

  ```
  dopamenu.dogeared.dev {
      tls { dns cloudflare {env.CLOUDFLARE_API_TOKEN} }
      reverse_proxy dopamenu-app:8080
  }
  dopamenu-auth.dogeared.dev {
      tls { dns cloudflare {env.CLOUDFLARE_API_TOKEN} }
      reverse_proxy dopamenu-keycloak:8080
  }
  ```

- **Keycloak must not run in dev mode.** `start-dev` with an in-memory database is fine for a
  laptop and wrong for a public host, so this service runs `start` with `KC_DB=postgres`,
  `KC_DB_URL=jdbc:postgresql://db:5432/keycloak`, `KC_DB_USERNAME=dopamenu`,
  `KC_DB_PASSWORD=dopamenu` — the same credentials the `db` service is created with, and the
  role that owns the database — plus `KC_PROXY_HEADERS=xforwarded`,
  `KC_HOSTNAME=https://dopamenu-auth.dogeared.dev` and `KC_HTTP_ENABLED=true`.
- `db-init/01-keycloak.sql` creates the `keycloak` database, because `POSTGRES_DB` only makes
  one. The directory is mounted at `/docker-entrypoint-initdb.d`, which Postgres runs **only
  on a fresh volume**: on an existing `dopamenu-public-pg` volume the statement is applied by
  hand once, and the deploy verifies it before starting Keycloak.
- Realm import runs on first start only: the client's `redirectUris` and `webOrigins` gain
  both public hostnames, and `post.logout.redirect.uris: "+"` then covers logout for them
  automatically.

**Smoke test from outside the local network** (the only version that proves anything):
on a phone with Wi-Fi off, load `/` and `/m/{token}`, complete registration and one order,
sign out and land back on `/`; then `curl -sI` the share URL from a machine off the LAN and
check the `X-Robots-Tag` header and the certificate chain. A smoke test run from the LAN
cannot fail the way an outsider fails.

### R3-1 — feasibility (blocking)

**Problem**

> The new `deploy/public/` section names a Caddyfile and one `compose.yaml` overlay, but never defines the process that runs Caddy. `deploy/dev-proxy/compose.yaml` is a separate Compose project (`name: dev-proxy`) that builds Caddy, publishes 80/443, mounts `./Caddyfile`, and persists certificates in the `caddy-data`/`caddy-config` volumes (its own comment: re-issuing on every restart hits ACME rate limits). The new text says `deploy/public/` is 'not a change to `deploy/dev-proxy/`' and then describes its single `compose.yaml` as overriding the app's loopback ports, so the file cannot also be the Caddy project. As written the Caddyfile has no container, no published 80/443 and no certificate volume, so the off-network smoke test has nothing to talk to.

**Remedy**

> State the ingress service explicitly: either a `deploy/public/compose.yaml` that both defines the Caddy service (image/build, published 80/443, Caddyfile mount, `/data` and `/config` volumes, restart policy) and overrides the app/keycloak ports, or a separate Caddy Compose project plus the overlay that puts `app` and `keycloak` on its network. Name the exact file `docker compose` is invoked with.

## Public-host ownership note (2026-11-04)

The `deploy/public/` plan in **Distribution Plan** is superseded. With the
Cloudflare tunnel and a central Keycloak now running from
`dogeared-central-infra`, a second Caddy and a second Keycloak in this repository would
duplicate infrastructure that already exists. The public host is a configuration in that
project; this repository owns the image, the realm export, the migrations and the
application behavior.

smoke test now live in `docs/deploy.md`. One consequence is recorded there explicitly:
the design's `/admin*` and `/realms/master*` denial is satisfied structurally, because
the app hostname routes only to this application, not to Keycloak. The realm changes
(self-registration, `dopamenu` login theme) are applied in `keycloak/realm-dopamenu.json`
as designed. Nothing about the event schema, the share lifecycle or the funnel queries
changes.
